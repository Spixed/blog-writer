# Blog Writer 个人开发者产品化实施方案

本文把 Blog Writer 从“可用的 P4 Web 项目”推进到“可发布、可升级、可恢复、可维护的桌面产品”。方案以当前仓库为基线：`packages/shared` 保存 `WorkspaceApi` 契约，`packages/server-node` 提供 Fastify 服务，`packages/frontend` 提供 React/Vite 编辑器，`electron` 提供桌面壳层。

目标不是一次性实现大型团队产品的全部能力，而是建立一个个人开发者能够长期维护的发布闭环：用户可以安全安装，数据不会因为升级或崩溃丢失，问题可以复现和定位，版本可以稳定交付。

## 1. 目标和边界

### 1.1 首个稳定版必须做到

- Windows、macOS、Linux 都有可下载构建物。
- 应用启动后自动启动本地后端，关闭时可靠停止后端。
- 工作区配置、文章写入、媒体上传和冲突状态在桌面环境与 Web 环境行为一致。
- 升级不会覆盖用户博客内容；升级失败可以重新安装旧版本继续打开数据。
- 每个发布版本都有校验哈希、变更日志、已知问题和回滚说明。
- CI 能在干净机器上完成 typecheck、构建、桌面打包和最小启动检查。

### 1.2 暂缓到稳定版之后

- 自动同步云端、账号系统和多人协作。
- 插件市场和第三方代码执行。
- 内置 Hugo 二进制分发。
- 复杂的崩溃上报服务和远程遥测。

这些功能会显著增加隐私、签名、兼容性和维护成本，不应阻塞第一个可发布版本。

## 2. 交付分层

每项工作按三个层次推进：

1. **MVP**：用户能使用，失败有明确提示，个人开发者能手工处理。
2. **稳定版**：自动化测试和 CI 覆盖主要失败路径。
3. **规模化**：当用户量或问题量证明需要时再增加服务和复杂度。

建议顺序为：数据安全与启动可靠性 → 安装包和发布 → 升级 → 测试矩阵 → 文档与反馈 → 高级扩展。

## 3. 桌面壳层完善

### 3.1 主进程职责

`electron/main.mjs` 只负责以下内容：

- 创建唯一的 BrowserWindow。
- 在回环地址启动 Fastify，使用随机可用端口。
- 将 `BLOG_ROOT`、`BLOG_NAME` 作为可选的首次启动参数。
- 监听后端启动失败、端口失败和窗口加载失败。
- 在 `before-quit` 中等待 `server.close()` 完成。
- 处理 macOS Dock 激活和所有窗口关闭行为。
- 通过 `setWindowOpenHandler` 只允许 `http`/`https` 外部链接交给系统浏览器。

主进程不直接读写文章，不实现第二套 API，不把 Node 能力暴露给渲染器。所有文章操作继续经过 `WorkspaceApi`，这样 Web 和 Electron 的行为可以共用测试。

### 3.2 安全基线

Electron 窗口必须保持：

```ts
webPreferences: {
  contextIsolation: true,
  nodeIntegration: false,
  sandbox: true,
}
```

后续若需要原生文件选择器，只添加最小 preload API，例如 `selectDirectory()`，不提供任意 `fs`、`child_process` 或 IPC 转发。每个 IPC 方法都要有参数校验、返回类型和调用方说明。

### 3.3 启动状态机

界面应区分以下状态，并为每种状态提供可操作的错误信息：

| 状态 | 用户看到的内容 | 操作 |
| --- | --- | --- |
| starting | 正在启动本地服务 | 等待、取消 |
| ready | 正常编辑界面 | 无 |
| server-failed | 服务启动失败及日志摘要 | 重试、打开日志目录、退出 |
| renderer-failed | 界面加载失败 | 重载窗口、打开日志目录 |
| shutting-down | 正在保存并退出 | 等待 |

启动失败日志写入 `app.getPath('logs')/main.log`，禁止把博客正文、访问令牌或完整环境变量写入日志。

### 3.4 单实例和异常退出

稳定版应增加：

- `app.requestSingleInstanceLock()`，第二次启动将已有窗口置前。
- 未保存草稿存在时，关闭窗口先询问“保存、放弃、取消”。
- 后端异常退出时，界面进入 `server-failed`，提供一次重启后端的按钮。
- 进程退出码和最后一次启动阶段写入日志，方便用户提交诊断信息。

验收：连续启动两个实例只保留一个窗口；杀掉后端进程后界面能恢复；关闭窗口后端端口释放；强制关闭应用不会修改未保存文章。

## 4. 数据安全和恢复

这是 Blog Writer 的核心竞争力。字节级 round-trip 不能只停留在测试中，还要成为用户可理解的安全承诺。

### 4.1 保存前快照

每次写入前，在博客根目录下创建受控备份目录，例如：

```text
.blog-writer/backups/<workspace-id>/<yyyy-mm-dd>/<timestamp>-<slug>-<lang>.md
```

规则：

- 只保存即将被覆盖的原始字节。
- 默认保留最近 20 个版本或最近 30 天，以先达到者为准。
- 备份写入成功后才执行正式替换。
- 清理备份失败不能阻塞保存，但要写日志。
- `.blog-writer` 加入 Hugo 忽略规则建议，不改变文章发布结果。

### 4.2 原子写入

`PostStore.write` 应采用：写入同目录临时文件 → `fsync`（可行时）→ `rename` 替换。临时文件名包含随机后缀，异常退出时下次启动清理超过 24 小时的临时文件。

验收：写入过程中杀死进程，原文件仍可解析；目标文件不存在时不会留下半截文件；Windows 文件锁存在时提示“文件被其他程序占用”，不静默覆盖。

### 4.3 冲突处理

保存请求携带读取时的文件指纹：大小、mtime、可选 SHA-256。服务端发现磁盘版本已变化时返回 `409 CONFLICT`，响应包括：

- 编辑器版本。
- 磁盘版本。
- 本地草稿。
- 文件路径。

界面提供“查看差异、采用磁盘版本、强制保存本地版本、另存为副本”四个选项。强制保存必须二次确认，并创建快照。

### 4.4 恢复入口

在工作区设置中增加“备份与恢复”：

- 浏览某篇文章的历史版本。
- 预览差异。
- 恢复为新文件或覆盖当前文件。
- 打开备份目录。
- 查看备份占用空间。

MVP 可以只支持按文件恢复；稳定版再增加按工作区打包导出。

## 5. 安装包、图标和签名

### 5.1 资源目录

建立：

```text
electron/resources/icon.ico
electron/resources/icon.icns
electron/resources/icon.png
```

同一品牌源图生成三种格式，不要在不同平台使用不同图形。图标应在 16、32、128、256、512 px 下检查边缘和透明背景。

### 5.2 版本策略

- `package.json.version` 使用 SemVer。
- `0.x` 表示 API 和数据格式仍可能变化。
- 第一个公开稳定版使用 `1.0.0`。
- 每次 tag 必须与 package 版本一致，例如 `v1.0.0`。
- 文章格式变化必须在 `CHANGELOG.md` 中说明迁移影响。

### 5.3 Windows

MVP 使用 NSIS 和 portable 双构建；稳定版配置代码签名证书。签名秘密放在 GitHub Actions Secrets，不提交证书文件。发布前验证：安装、卸载、覆盖安装、用户数据保留、开始菜单快捷方式、Windows Defender 无明显拦截。

### 5.4 macOS

稳定版配置 Apple Developer ID Application 证书和 notarization。Secrets 至少包括证书、密码、团队 ID、API Key。验证 Intel 和 Apple Silicon 架构；若只构建 arm64，README 必须明确说明。

### 5.5 Linux

优先 AppImage，DEB 作为补充。验证 Ubuntu LTS 干净虚拟机启动、文件选择、中文字体、系统代理和 Hugo 命令调用。后续用户量足够再考虑 Flatpak 或 Snap。

### 5.6 发布流水线

`.github/workflows/electron.yml` 应分为：

1. `check`：安装、typecheck、lint、核心测试。
2. `package`：三平台构建并上传 artifact。
3. `release`：仅 tag 触发，生成 GitHub Release、校验哈希和变更日志。

每个平台都上传：安装包、`.blockmap`（如生成）、`checksums.txt`、构建日志摘要。GitHub Release 使用草稿状态，维护者检查后再发布。

## 6. 自动更新

个人开发者的推荐路线：

### MVP

- 应用启动时请求 GitHub Releases API。
- 有新版本时显示版本号、发布日期和变更摘要。
- 用户点击后打开 Release 页面手动下载。
- 不自动下载、不自动替换文件。

### 稳定版

加入 `electron-updater` 或等价方案，但必须满足：

- 仅检查签名发行物。
- 默认只提示，不后台安装。
- 用户确认后下载。
- 安装在退出时执行。
- 更新失败保留旧版本。
- 提供“跳过此版本”和“稍后提醒”。

自动更新前先完成代码签名，否则更新会降低用户信任和系统安全。

## 7. 测试和质量门禁

当前已有 round-trip、schema、blocks、render、UI smoke、浏览器布局/交互/性能测试。下一步不要重复增加实现镜像测试，而是覆盖真实故障边界。

### 7.1 CI 分层

每个 Pull Request：

```text
typecheck → lint → server round-trip → frontend prose/schema/blocks → frontend build
```

每个 tag：

```text
全部 PR 检查 → 三平台打包 → 安装包 smoke → 上传 artifact → 草稿 Release
```

### 7.2 Electron smoke 测试

使用 Playwright 或 Spectron 的替代方案启动已打包应用，检查：

- 窗口在 30 秒内出现。
- `/api/health` 返回成功。
- 工作区列表可读取。
- 打开一篇中英文文章。
- 修改标题并保存，文件字节符合预期。
- 关闭应用后重新打开，文章仍存在。
- 后端端口释放。

Windows、macOS、Linux 至少各运行一次；本地开发不必每次三平台都跑，可以由 tag workflow 完成。

### 7.3 数据测试矩阵

固定 fixture 覆盖：

- CRLF 和 LF。
- UTF-8 BOM。
- 中文、英文、emoji、组合字符。
- Hugo shortcode、raw HTML、复杂代码块、数学公式。
- 40 KB 以上混合文档。
- 文件被外部编辑器修改。
- 文章被删除、重命名、媒体目录不存在。

### 7.4 性能预算

以当前 P4 基准为起点，稳定版记录：

- 5 万字文章首次打开时间：目标 < 2 秒。
- 普通输入 p95 延迟：目标 < 50 ms。
- 保存反馈：目标 < 300 ms（不含磁盘异常）。
- 空闲内存：目标 < 350 MB；大文档编辑峰值单独记录。
- 无连续 50 ms 以上 long task。

CI 只做趋势记录，不把不同运行器的绝对数值当成硬失败条件；超过预算连续两次才阻塞发布。

## 8. 错误报告和隐私

个人项目不建议首日接入复杂 SaaS。先实现本地诊断包：

- 应用版本、操作系统、架构。
- 启动阶段和最近 1000 行日志。
- 后端健康状态、构建信息。
- 不包含文章正文、路径中的用户名、环境变量、媒体内容。

用户主动点击“导出诊断信息”后生成 zip，并在界面显示将导出的字段。日志中对路径做脱敏，例如只保留盘符和最后两级目录。

当 Issue 数量超过每月 10 个或无法稳定复现时，再接入 Sentry 等服务；启用前必须提供设置中的遥测开关和隐私说明。

## 9. 文档体系

补齐以下文件：

```text
CHANGELOG.md
docs/user-guide.zh-CN.md
docs/user-guide.en.md
docs/release-runbook.zh-CN.md
docs/troubleshooting.zh-CN.md
docs/privacy.md
.github/ISSUE_TEMPLATE/bug.yml
.github/ISSUE_TEMPLATE/feature.yml
.github/PULL_REQUEST_TEMPLATE.md
```

### 用户手册必须覆盖

- 安装和首次启动。
- 添加 Hugo 工作区。
- 三种编辑模式的适用场景。
- 保存、自动保存和冲突处理。
- 媒体管理。
- Hugo 检查和预览。
- 备份恢复。
- 日志和诊断包。
- 卸载是否保留工作区配置。

### 发布 Runbook

每次发布按固定顺序执行：

1. 更新版本号和 CHANGELOG。
2. 在干净工作区执行全部检查。
3. 创建 `vX.Y.Z` tag。
4. 等待三平台构建。
5. 下载 artifact，在至少一个真实系统安装。
6. 检查启动、打开文章、保存、退出、升级。
7. 校验哈希和签名。
8. 发布 GitHub Release。
9. 在 Discussions 或 README 公布升级说明。
10. 保留旧版本下载链接和回滚说明。

## 10. 可访问性、快捷键和国际化

稳定版最低要求：

- 所有工具栏按钮有可访问名称和 tooltip。
- 菜单、弹窗、媒体对话框支持键盘完成和 Escape 关闭。
- 焦点顺序稳定，不能只依赖颜色表达冲突或错误。
- 明暗模式对比度通过检查。
- 中文和英文 UI 文案集中管理，不在组件中散落硬编码。
- 快捷键表可在设置中查看，并允许冲突检测。

优先补齐的快捷键：保存、切换模式、搜索、替换、打开工作区、下一篇/上一篇、关闭弹窗、撤销/重做。

## 11. 导入、导出和批量操作

### MVP

- 导出当前文章原始 Markdown。
- 导出当前工作区配置 JSON，不包含正文以外的秘密。
- 批量删除前显示文件清单并要求确认。
- 批量操作全部写入备份。

### 稳定版

- 工作区打包为 zip：文章、媒体、配置、版本信息。
- 导入前预览冲突文件。
- 支持只导入文章、只导入媒体、只恢复配置。
- 导入失败可以回滚整个批次。

## 12. 插件和扩展的克制路线

不要直接开放任意 JavaScript 插件。先定义只读扩展点：

- 自定义渲染器注册表。
- 自定义 shortcode schema。
- 命令和快捷键注册。
- 导入/导出转换器。

插件清单包含名称、版本、权限和兼容的 Blog Writer 版本。第一版插件运行在渲染器或独立 worker 中，不能访问任意文件系统。等 API 稳定后再考虑写入权限。

## 13. 单人维护节奏

建议按月维护，而不是追逐所有高星项目功能：

- 每周：处理崩溃、数据损坏和安装失败问题。
- 每两周：合并小功能和依赖升级。
- 每月：发布一个补丁或 minor 版本，更新 CHANGELOG。
- 每季度：跑一次三平台完整安装/升级/恢复演练。

每次变更都回答三个问题：是否可能改变 Markdown 字节、是否影响已有工作区、失败后用户如何恢复。

## 14. 推荐里程碑

### R1：可发布桌面 Alpha

- 图标、版本号、启动状态、单实例。
- 三平台未签名安装包。
- Electron smoke 测试。
- 用户手册和故障排查文档。

验收：陌生用户能从 Release 下载并打开自己的 Hugo 站点。

### R2：数据安全稳定版

- 原子写入、保存前快照、冲突 UI、恢复入口。
- 诊断包、日志脱敏。
- 安装/覆盖安装/卸载测试。

验收：模拟进程崩溃、外部修改和写入失败，文章可恢复且无静默覆盖。

### R3：正式 1.0

- Windows/macOS 签名，macOS notarization。
- 自动更新提示或签名更新。
- tag 发布、哈希、CHANGELOG、回滚 Runbook。
- 关键路径三平台验证。

验收：从 `0.x` 升级到 `1.0`，已有工作区和文章无需迁移即可打开。

### R4：生态和规模化

- 工作区打包导入导出。
- 只读插件 API。
- 可选遥测和崩溃服务。
- 性能趋势看板。

只有在真实用户反馈证明需求存在时进入 R4。

## 15. 第一周可执行任务清单

1. 在 `electron/resources` 加入三平台图标。
2. 给主进程加单实例、启动失败页面和日志文件。
3. 为保存增加原子写入和保存前快照。
4. 在 `WorkspaceApi` 增加冲突错误类型和前端恢复 UI。
5. 建立 Electron smoke 脚本并接入 tag workflow。
6. 创建 `CHANGELOG.md`、用户手册、隐私说明和 Issue 模板。
7. 手动执行一次 Windows 安装、覆盖安装、卸载和数据保留演练。
8. 为第一个 Alpha tag 生成三平台 artifact，暂不启用自动更新。

完成这八项后，项目就从“能封装”进入“可以交给真实用户试用”的阶段；签名、自动更新、插件和遥测都可以建立在这套可靠基础上。
